# Contributing

This is the canonical guide to developing and releasing neumera.

## Setup

Prerequisites: [uv](https://docs.astral.sh/uv/), [just](https://just.systems/), [rustup](https://rustup.rs/), and [elan](https://github.com/leanprover/elan). The Rust toolchain version is pinned in `rust-toolchain.toml` and installed automatically by rustup; the Lean toolchain is pinned in `lean-toolchain` at the repository root (`lean/lean-toolchain` is a symlink to it, so Lake and elan find it from either place) and installed automatically by elan the first time `lean` or `lake` runs; uv manages Python and all Python tooling.

```sh
git clone https://github.com/jakeryderv/neumera.git
cd neumera
just setup
```

`just setup` installs dependencies, builds the Rust extension in development mode, and enables the git hooks.

## Layout

| Path | Contents |
|---|---|
| `lean/` | Lake package: Lean definitions and proofs (`Neumera/`), the contracts module (`Neumera/Contracts.lean`), and the manifest emitter (`Manifest.lean`) |
| `rust/` | Cargo workspace; the version lives in its `Cargo.toml` |
| `rust/neumera-lean/` | Lean integration crate: runs Lake and the manifest emitter from `build.rs`, validates build identity, generates `contracts`, links the Lean library. No Python dependency. Name provisional |
| `rust/neumera-py/` | PyO3 adapter, compiled to the `neumera._core` extension module. Does not yet depend on `neumera-lean` |
| `scripts/` | `contract_negative_tests.py`: mutations that must fail the Rust build |
| `src/neumera/` | Python package; re-exports the public API from `_core` |
| `docs/` | Design documents; start with `bringing-mathematical-meaning-into-everyday-programming.md` |
| `src/neumera/_core.pyi` | Type stubs, **generated** from the compiled extension |
| `tests/` | Python tests (Rust unit tests live next to the Rust code) |

## Everyday commands

Run `just` to list all recipes.

| Command | What it does |
|---|---|
| `just dev` | Rebuild the extension and regenerate `_core.pyi` |
| `just test` | Rebuild, then run pytest and `cargo test` |
| `just fmt` | Format Python and Rust |
| `just lint` | Lockfile check, ruff, ty, clippy |
| `just check` | Everything CI's check job runs: build, format check, lint, tests |
| `just negative-tests` | Contract manifest negative tests (CI's `contracts` job); a few minutes |
| `just lean` | Build the Lean library alone (the Rust build script does this too) |
| `just commit` | Write a commit interactively (Conventional Commits prompt) |

Run `just dev` after changing Rust code. The git hooks run `just fmt-check lint` before each commit and check the commit message format (see below); bypass them with `git commit --no-verify` if you need to.

### Lean and the contract manifest

The `neumera-lean` build script runs `lake build` in `lean/`, then runs `lean/Manifest.lean` to audit every theorem in `Neumera.Contracts` (axioms must be in the allowlist; `sorry` fails the build) and write `lean/.lake/build/contracts-manifest.json`. It recomputes the hashes of the static library, the checked `.olean` files, and `lake-manifest.json`, compares them with the manifest, and only then generates `contracts.rs` with one constant per contract. A Rust rule that relies on a contract references its constant. Lake is incremental, so a no-op rebuild costs about a second. Set `NEUMERA_LEAN_MANIFEST=<path>` to validate a supplied manifest in place of the emitted one; the emitter still runs, the supplied file must match its contract metadata and module set exactly, and only the recorded identity can differ. The negative tests use this to prove a stale or tampered manifest is rejected.

To add a contract: prove the theorem in `lean/Neumera/`, restate it in `lean/Neumera/Contracts.lean` with a doc comment `export: <symbol>`, reference the generated constant from the Rust rule, and add a negative-test case if the new contract introduces a new way to drift.

### Type stubs

`_core.pyi` is generated by `just dev` (via `maturin develop --generate-stubs`) and committed. Don't edit it by hand. CI fails if the committed stub differs from a fresh build, so commit the regenerated file along with the Rust change that caused it.

## Commits and pull requests

- Use [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<optional scope>)<optional !>: <description>`, where type is one of `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- Three ways to write a commit, all checked the same way:
  - `git commit -m "feat: ..."` as usual.
  - `git commit` opens your editor with a template listing the types and examples (enabled by `just hooks`).
  - `just commit` walks you through an interactive prompt ([commitizen](https://commitizen-tools.github.io/commitizen/)).
- If the message check rejects a commit, your message is kept: `git commit -e -F .git/COMMIT_EDITMSG` reopens it for editing. If a `just commit` fails (for example, the pre-commit lint fails), fix the problem and run `just commit --retry` to reuse your answers.
- Pull requests are squash-merged, and the PR title becomes the commit message, so give PRs conventional titles too.
- Both are enforced by `cz check`: locally by the `commit-msg` hook, and in CI by the `pr-title` check.
- `main` is protected against force-pushes and deletion. PRs need the `ci-ok` and `pr-title` checks to pass; the maintainer can push to `main` directly.
- Work on a branch and open a draft PR as soon as you push it (`gh pr create --draft --fill`). CI runs on pull requests and on pushes to `main`, not on other branch pushes, so a branch without a PR gets no CI unless you dispatch it by hand (`gh workflow run CI.yml --ref <branch>`).
- The PR template has a checklist. Changes to `rust/neumera-lean/build.rs`, `unsafe` code, `lean/Manifest.lean`, or the manifest format get an independent adversarial review before merge; record its findings in the PR.
- Merge with `gh pr merge --squash --delete-branch`. If another PR is stacked on the one being merged, retarget it to `main` first (`gh pr edit <n> --base main`): deleting the base branch closes a stacked PR, and a closed PR whose base is gone cannot be reopened. GitHub deletes the remote branch on merge; the flag also deletes your local branch and checks out `main`. Squash merges rewrite history, so `git branch -d` on a merged branch refuses with "not fully merged"; that flag or `git branch -D` is the answer. A plain `git fetch` prunes stale `origin/*` refs (`fetch.prune` is recommended globally); a fetch with an explicit branch argument prunes only that branch.

## CI

`.github/workflows/CI.yml` runs on pushes to `main` and on pull requests:

- **check**: installs Lean with `leanprover/lean-action`, then `just check` and the stub check, on Python 3.12 and 3.14.
- **contracts**: the manifest negative tests (`scripts/contract_negative_tests.py`).
- **wheels**: builds wheels where Lean ships a prebuilt toolchain: x86-64 and aarch64 Linux (manylinux_2_28, since Lean needs glibc 2.26+), Apple Silicon macOS, plus the sdist. Intel macOS and x86-64 Windows are built best-effort and don't block `ci-ok`.
- **test-wheels**: installs the built wheels and runs the tests on each platform that can run them natively.
- **ci-ok**: a single job that passes only if all of the above passed; this is a required check.

`.github/workflows/pr-title.yml` checks pull request titles (the other required check). It reruns when a title is edited, without rerunning the full CI.

## Dependencies

Dependabot opens weekly grouped PRs for GitHub Actions, Cargo, uv, and the Rust toolchain. The Lean binding crates (`lean-rs-sys`, `lean-rs-abi`) are pinned to a commit of the project's fork through `[patch.crates-io]` in `rust/Cargo.toml` and are updated by hand; see `docs/binding-layer-evaluation.md`. It has no support for elan or Lake, so the Lean toolchain pin in `lean-toolchain` and any Lake dependencies are updated by hand. Before bumping the Lean pin, check that `lean-rs-sys` supports the new version (see `docs/binding-layer-evaluation.md`), and update `ELAN_TOOLCHAIN` in `.cargo/config.toml` to the same value; the build fails if the two disagree. The bindings rebuild on their own after a pin change, and the build fails if `lean-rs-sys` and Lake resolved different toolchains. `NEUMERA_ALT_TOOLCHAIN=<installed toolchain> just negative-tests` exercises both.

- GitHub Actions updates and minor/patch uv updates merge automatically once CI passes.
- Cargo and Rust toolchain updates need a manual merge. A pyo3 bump can change the generated stubs: check out the PR, run `just dev`, and commit the updated `_core.pyi`.

## Releasing

The version lives only in `rust/Cargo.toml`. Releases are published to PyPI by `.github/workflows/publish.yml` using trusted publishing.

1. On a clean, up-to-date `main`, run `just release X.Y.Z`. This bumps the version, runs `just check`, then commits and tags `vX.Y.Z` locally.
2. Push: `git push origin main && git push origin vX.Y.Z`.
3. The publish workflow verifies that the tag matches the version, rebuilds and tests everything, then waits for approval on the `pypi` environment. Approve it from the workflow run page.
4. After publishing, the workflow creates a GitHub Release with generated notes and the built files attached.

PyPI never allows reusing a version number, even after deleting a release.
