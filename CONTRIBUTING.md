# Contributing

This is the canonical guide to developing and releasing neumera.

## Setup

Prerequisites: [uv](https://docs.astral.sh/uv/), [just](https://just.systems/), and [rustup](https://rustup.rs/). The Rust toolchain version is pinned in `rust-toolchain.toml` and installed automatically by rustup; uv manages Python and all Python tooling.

```sh
git clone https://github.com/jakeryderv/neumera.git
cd neumera
just setup
```

`just setup` installs dependencies, builds the Rust extension in development mode, and enables the git hooks.

## Layout

| Path | Contents |
|---|---|
| `rust/` | Rust crate (PyO3), compiled to the `neumera._core` extension module |
| `src/neumera/` | Python package; re-exports the public API from `_core` |
| `src/neumera/_core.pyi` | Type stubs, **generated** from the compiled extension |
| `tests/` | Python tests (Rust unit tests live next to the Rust code) |

## Everyday commands

Run `just` to list all recipes.

| Command | What it does |
|---|---|
| `just dev` | Rebuild the extension and regenerate `_core.pyi` |
| `just test` | Rebuild, then run pytest and `cargo test` |
| `just fmt` | Format Python and Rust |
| `just lint` | Lockfile check, ruff, ty, clippy |
| `just check` | Everything CI's check job runs: build, format check, lint, tests |
| `just commit` | Write a commit interactively (Conventional Commits prompt) |

Run `just dev` after changing Rust code. The git hooks run `just fmt-check lint` before each commit and check the commit message format (see below); bypass them with `git commit --no-verify` if you need to.

### Type stubs

`_core.pyi` is generated by `just dev` (via `maturin develop --generate-stubs`) and committed. Don't edit it by hand. CI fails if the committed stub differs from a fresh build, so commit the regenerated file along with the Rust change that caused it.

## Commits and pull requests

- Use [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<optional scope>)<optional !>: <description>`, where type is one of `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- Write commits with `just commit` for an interactive prompt ([commitizen](https://commitizen-tools.github.io/commitizen/)), or with plain `git commit` as usual. If a `just commit` fails (for example, the pre-commit lint fails), fix the problem and run `just commit --retry` to reuse your answers.
- Pull requests are squash-merged, and the PR title becomes the commit message, so give PRs conventional titles too.
- Both are enforced by `cz check`: locally by the `commit-msg` hook, and in CI by the `pr-title` check.
- `main` is protected against force-pushes and deletion. PRs need the `ci-ok` and `pr-title` checks to pass; the maintainer can push to `main` directly.

## CI

`.github/workflows/CI.yml` runs on pushes to `main` and on pull requests:

- **check**: `just check` and the stub check, on Python 3.12 and 3.14.
- **wheels**: builds wheels for Linux (glibc and musl), macOS, and Windows across architectures, plus the sdist.
- **test-wheels**: installs the built wheels and runs the tests on each platform that can run them natively.
- **ci-ok**: a single job that passes only if all of the above passed; this is a required check.

`.github/workflows/pr-title.yml` checks pull request titles (the other required check). It reruns when a title is edited, without rerunning the full CI.

## Dependencies

Dependabot opens weekly grouped PRs for GitHub Actions, Cargo, uv, and the Rust toolchain.

- GitHub Actions updates and minor/patch uv updates merge automatically once CI passes.
- Cargo and Rust toolchain updates need a manual merge. A pyo3 bump can change the generated stubs: check out the PR, run `just dev`, and commit the updated `_core.pyi`.

## Releasing

The version lives only in `rust/Cargo.toml`. Releases are published to PyPI by `.github/workflows/publish.yml` using trusted publishing.

1. On a clean, up-to-date `main`, run `just release X.Y.Z`. This bumps the version, runs `just check`, then commits and tags `vX.Y.Z` locally.
2. Push: `git push origin main && git push origin vX.Y.Z`.
3. The publish workflow verifies that the tag matches the version, rebuilds and tests everything, then waits for approval on the `pypi` environment. Approve it from the workflow run page.
4. After publishing, the workflow creates a GitHub Release with generated notes and the built files attached.

PyPI never allows reusing a version number, even after deleting a release.
